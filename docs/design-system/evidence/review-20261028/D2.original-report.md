实际源码观察：

- `training/estimation/index.wxml` 的滑杆通过 catchtouchstart/move/end 处理拖动，展示 A/X 分配。index.js 的 handleTouchMove 在页面内把位置限制到 5–95%，并计算 userA/userX；submitAnswer 计算理论值、偏差和等级，写 records，再设置 submitted。它不是可直接配置的通用手势组件，也不能把这些业务公式移入公共层。上述数值仅为源码现值，未获设计批准。
- estimation 的“确认答案”在当前模板中始终存在，“下一题”由 submitted 控制；抽读的提交函数没有提交状态前置保护。这里只记录事实和重复触发风险，不判定必须锁定、不改评分或现有交互。滑杆模板未列 catchtouchcancel；手写 canvas 则明确处理 cancel。新手势需明确取消行为，不能照抄局部实现当完整协议。
- `training/session/index.js` 有手写坐标/笔画逻辑，计时使用 Date.now 差值展示已用时；提交在页面内验证答案、记录、递增答题数、切题或完成。`cognition/session/index.js` 另有 elapsed tick 与 countdown 到零回调及卸载清理。计时形态不同，不能把“计时”统一解释为新的限时截止规则。

## 复用、配置、扩展、新建的选择

1. 复用：确认、下一题等外围普通操作优先评估现有 btn-base recipe；进度展示遵守 PAT-PROGRESS 输入契约。复用角色和已有语言，不把 draft 数值升级为 approved，不带入评分、业务计时或完成判断。
2. 配置：优先利用已有主次按钮、尺寸和模块主题能力，仅在真实角色匹配时选择；保留行测速练皮肤及流式/固定布局的原有职责。尚无依据提出新尺寸、颜色或灵敏度值。
3. 扩展：如果后续确认手势生命周期、坐标处理、状态和事件在多个训练任务中相同，可在训练域抽出最小展示/输入能力，并列出真实消费者。当前未证明这类可配置抽象，也不应直接扩展全局按钮来承载手势、倒计时和评分。
4. 新建：推荐新专项核心为 C 类，最初仅服务新增限时手势任务。现有 estimation 是带 A/X 分配、偏差判断和 records 的页面实现；session 是手写辅助与作答切题；cognition 的 countdown 是另一任务运行方式。直接整页复制或把三者揉进通用组件会把业务规则带入共享层。C 类独立符合已批准原则，无需为“不能机械复用”反复请求逐项审批。

建议未来核心输入限于内容/任务身份、展示参数和业务状态，输出手势开始/更新/结束/取消与操作意图；业务模块决定限时截止、提交是否有效、答案/偏差、成绩、统计和持久化。具体事件名、时长与截止竞态策略是待设计项。本场景未给出精确手势任务，不能把以上边界建议写成已批准 API。
