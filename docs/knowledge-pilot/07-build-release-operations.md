# 07 构建发布与维护

> 状态：流程已确认；政治模块最终打包位置和内容更新方式待实现时确定

## 构建原则

- Markdown 是正式编辑源，运行时 JSON/JS 是派生产物。
- 构建不依赖 Obsidian 进程、主题或社区插件。
- 同一来源、知识文件和工具版本产生确定性输出。
- 任何正式输出都带知识包版本和来源版本。
- 不直接修改生成文件修复问题。

首批接入不一次实现下述全部能力。具体按“协议校验器 → 预览构建器 → 完整构建器”推进，见 [10-Obsidian 与构建器接入时序](./10-obsidian-builder-rollout.md)。

## 构建步骤

```text
审核通过的 Markdown
        ↓
解析属性、正文和卡片
        ↓
解析稳定 ID、目录和内部链接
        ↓
校验来源、状态、关系和内容结构
        ↓
生成知识点、目录、地图、反向关系、搜索和卡片索引
        ↓
生成政治模块知识包
        ↓
运行数据、包体和页面检查
        ↓
生成构建报告和可发布版本
```

## 生成产物

政治知识包至少包含：

- 模块元信息。
- 正式目录。
- 知识点运行时内容。
- 地图节点与边。
- 搜索索引。
- 速记卡索引。
- 来源版本摘要。
- 知识包版本和构建时间。

运行时不携带完整 OCR 中间证据；证据保留在本地仓库，用于审计和更新。

## 版本规则

建议区分：

- `sourceVersion`：原始资料集合版本。
- `contentVersion`：政治 Markdown 内容版本。
- `schemaVersion`：内容协议版本。
- `packageVersion`：小程序政治知识包版本。

修改排版但不改变事实时仍产生新知识包版本；修改来源或事实时同时更新内容版本和受影响知识点版本。

## 发布门禁

发布前按顺序执行：

1. 来源文件和证据完整性检查。
2. OCR 差异、高风险和事实校对门禁。
3. Markdown 协议、链接和状态检查。
4. 目录、地图、卡片和搜索索引检查。
5. 小程序运行时结构与包体检查。
6. 核心页面视觉走查。
7. 生成批次验收单和构建报告。

任一步失败，不生成或不标记正式发布版本。

## 预览与正式发布

- `approved` 内容可以进入本地预览包。
- 只有批次验收完成后，内容状态才可进入 `published`。
- 预览包和正式包使用不同版本标记，避免误上传。
- 首个政治模块优先随小程序代码发布，待更新频率和包体证明需要后再评估云端内容包。

## 回滚

每次正式发布保存：

- 上一个知识包产物。
- 构建所用 Markdown 提交。
- 来源和工具版本。
- 构建报告和验收单。

回滚只切换到上一个通过验收的知识包，不在生产数据中手工删改。用户本地进度按稳定 ID 保留；若版本删除了知识点，按迁移表处理。

## 内容更新

更新流程：

1. 新资料作为新来源版本进入 `sources`。
2. 计算变化页和受影响证据单元。
3. 将相关审核和知识点标记为 `stale`。
4. 只重新审核受影响内容，但完整运行全局链接和发布门禁。
5. 生成新知识包和变更说明。

不得用新 OCR 全量静默覆盖已经人工审核的 Markdown。

## 运行报告

每次构建输出：

- 来源文件和页数。
- 各状态知识点数量。
- 证据覆盖率。
- 未解决差异和高风险数量。
- 断链、孤立节点和循环前置关系。
- 卡片覆盖率。
- 生成文件及体积。
- 与上一版本的新增、修改、删除。

## 维护边界

- OCR 规则维护在源文流水线，不散落在知识卡生成器。
- 内容字段维护在 Markdown 协议，不由页面临时猜测。
- 地图关系维护在知识模型，不在 WXML 中硬编码。
- 复习规则维护在学习流，不写入知识正文。
- 政治特有规则写入执行手册或政治模块规范，不污染通用协议。
