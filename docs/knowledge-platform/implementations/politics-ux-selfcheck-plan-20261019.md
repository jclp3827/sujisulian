## 3. U1 自查执行方法

### 3.1 从入口和状态覆盖，不按截图数量算覆盖率

依据自查表覆盖首页、搜索、图谱、正文、四条路线和占位页。同一物理路线页必须分别检查四种路线，不因共用模板就记成全部通过。

每个状态记录：入口 → 当前界面 → 主动作 → 次动作 → 返回目标 → 进度恢复。以用户截图作为初始问题证据，以当前构建的实际交互确认现状。

源码检查区分：可见文字、条件隐藏文字、无障碍标签、数据状态枚举、历史文档和内部日志。不得批量替换所有“正式”“关系”“范围”等词；只有暴露内部实现或没有操作价值的表述才调整。

### 3.2 每项检查的固定问题

1. 用户能否先看懂“这里做什么、当前对象、下一步点哪里”？
2. 同一范围、数量、阶段或操作是否重复说明？
3. 页面头部是否抢占了实际学习内容的位置？
4. 状态或提示是否必要，是否可折叠或并入对象本身？
5. 当前阶段是否有明确的主动作？自评等成组选择是否有清楚的整体职责？
6. 主动作位置是否随状态无规律漂移？调整、退出是否与主动作竞争？
7. 是否存在不必要的输入、确认、强制打开或中转页面？
8. 字体、图标、边距、卡片、箭头和按钮是否消费同角色 token？不同颜色是否仍属同一套交互？
9. 简化后是否保留真实的范围限制、错误恢复、阶段和进度含义？
10. 当前界面是否有真实交互证据，而非只有源码或字符串断言？

### 3.3 信息与操作原则

- 页面主要呈现操作对象和学习内容。普通操作说明目标为一句；进行状态目标为“进度一行、操作提示一行”。长标题和必要错误允许换行，不通过截断知识或缩小正文硬凑行数。
- 同一信息只设一个主要位置；同一动作原则上只保留一个当前可见入口。
- 连续任务的阶段主动作使用统一底部区域；范围调整跟随范围卡；导航返回优先承担离开职责。快速导读的段内展开和目录整行跳转保持内容上下文，不机械地把所有按钮悬浮。
- 需要滚动的正文须给底栏留足空间；不能遮挡最后一段、自评选择、提示或错误。自评组不是多个互相竞争的主 CTA。
- “即点即走”用于快速了解；不能据此删除系统学习和速记自身的揭晓、自评等核心操作。
- 使用现有字体、控件和间距角色，不先新增另一套数值。基线包含正文/标题/辅助文字角色、按钮文字双轴居中、箭头视觉尺寸与点击热区分开。既有统一箭头缩小到 80% 的决定保留，不再次累计缩放。
- 其他模块 token 不一致时登记“角色映射/后续对齐建议”，本轮不修其他模块，不以它们任何一个页面作为绝对标准。

## 4. 从自查结果到修复路径

每条问题使用唯一 ID，必须有页面与状态、证据、用户影响、根因层和预计消费者。根因标记为：文案 / 页面编排 / 操作流程 / 组件 / token / 内容来源。

路径固定为：

`截图或现场问题 → 当前消费者确认 → 归类与优先级 → 所属批次 → 最小改动 → 当前状态验证 → 更新该问题结果`

优先级：

- P0：阻断继续、按钮无效、返回错误、进度丢失。当前发现时优先处理，仅修其最小影响范围。
- P1：误导下一步、内部语言外露、强制无必要输入、核心动作或对象难找。
- P2：重复说明、视觉主次和字号图标间距不一致。

纯文案不能承担状态或事实来源修复。涉及完成条件、两侧依据门槛和旧存储时，必须把行为变化和兼容策略写入本批清单；不能通过删除按钮让旧状态机不可达，也不能把历史输入伪装成新用户已作答。

## 5. 验证与停止条件

- U0：只验证文档链接、登记和差异范围，不运行整个产品测试。
- U1：读取与实际交互分开记录；工具不可用则标为阻塞，不伪报通过。
- U2–U6：每批先检查变更范围及相关自动门禁，再做本批状态和往返验证。可逆文案不增加仅镜像字符串的测试；状态规则变化须有行为验证。
- 本地交互前另存本批进度快照，结束逐项恢复；不覆盖既有原始备份，不清空全部缓存。
- 自动权限审查是工具执行条件，不是产品批次，不通过新增审查工作解决。失败须记录动作是否执行、数据是否已恢复，不能绕过。
- 已有 R1/R2 和部分 R3 为旧构建/旧状态证据。新批次影响到的路径需重新验证；未受影响证据可引用但标明来源，不重复全量跑测。
- 本轮最后只做实际修复流程的必要联测和简报，无独立资料审查或文档治理批次。工程验证、用户验收和发布分别说明。
